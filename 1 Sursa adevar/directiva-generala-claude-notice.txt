REGULA GENERALA DE DENUMIRE

Pentru numele alese de noi, prefera denumiri lungi,
ne-generice si auto-explicative, care spun simultan:
- ce categorie de obiect este;
- ce rol concret are obiectul.

Numele tehnice impuse de Claude Code raman neschimbate,
de exemplu UserPromptSubmit, PreToolUse, Stop etc.

Fisierul existent
"1 Sursa adevar/daca_detecteza_cuvinte_in_prompt_atunci_insereaza_asta.txt"
ramane cu aceasta denumire.

REGULA CLAUDE CODE NOTICE - CCN

CCN trebuie sa fie FOARTE SCURT.

Forma de baza pentru fiecare actiune vizibila este:

<nume folder hook in repo> a facut X.

Nu pune in CCN dumpuri tehnice, hashuri, commituri, cai de fisiere de infrastructura,
liste lungi, continut complet de remindere, validari detaliate sau explicatii de debug,
exceptand cazul in care o eroare critica nu poate fi inteleasa altfel.

Scopul CCN este doar sa confirme rapid utilizatorului:
- ce hook/folder a rulat;
- ce actiune principala a facut.

EXCEPTIE PENTRU EROAREA JURNALIZARII

Daca helperul comun nu poate finaliza jurnalizarea persistenta, mesajul nu are voie
sa spuna vag doar ca nu a putut scrie "log tehnic.txt". Programul trebuie sa produca
un diagnostic comun care precizeaza cel putin:
- etapa exacta care a esuat: lock, pregatire/clonare repository, pull, scrierea fiecarui
  fisier, git add, commit, pull dupa push respins sau push/reincercare;
- codul erorii si mesajul/stderr relevant;
- repository-ul local si remote implicat;
- daca ambele loguri au fost deja scrise local;
- unde a fost salvata copia locala fallback a diagnosticului sau de ce nici aceasta
  nu a putut fi salvata.

Datele sensibile din mesaj, stderr ori URL se mascheaza inainte de afisare.
Valoarea exacta a credentialului de logging se mascheaza chiar daca nu are un prefix
standard GitHub.

Acelasi diagnostic comun se trimite simultan:
1. in CCN/systemMessage, chiar daca pentru aceasta eroare critica CCN devine mai lung;
2. in additionalContext, impreuna cu instructiunea explicita pentru Claude sa il afiseze
   distinct si integral LA SFARSITUL raspunsului curent catre utilizator, sub titlul
   "⚠️ JURNALIZAREA HOOKURILOR A ESUAT", chiar daca sarcina principala a reusit.

Nu pretinde ca jurnalizarea persistenta a reusit. Daca procesul hookului este terminat
brutal inainte sa poata emite output, nici CCN, nici additionalContext nu pot fi garantate.

REGULA LOG ACTIVITATE HOOKS

Implementarea canonica unica pentru logging este:
shared/program_scrie_log_activitate_hooks.mjs

Toate hookurile existente si viitoare folosesc acest helper.
Nu crea logger separat intr-un hook; daca se schimba destinatia sau formatul logului,
schimbarea se face in helperul comun.

Detaliile se scriu persistent in repository-ul separat:

ion-motica/YL-Claude-garduri-Log-hooks-scris-de-Claude

Exista DOUA fisiere de log, produse de acelasi helper comun si acelasi apel al gardului:

1. log human readable.txt
   - jurnal scurt si usor de citit de om;
   - fiecare inregistrare incepe cu:
     =======================================
     data/ora;
     titlul chatului;
     promptul trimis de utilizator lui Claude;
   - dupa antet, fiecare gard activat este afisat SEPARAT, in ordinea activarii;
   - pentru fiecare gard, titlul este chiar numele folderului gardului din repo;
   - sub titlu se scrie numai ce este relevant, de exemplu:
     "Nu a detectat nimic de facut.";
     "A inserat in CCN:" + continutul;
     "A inserat in additional context:" + continutul;
     "A blocat activarea uneltei X pentru Y." + motivul scurt;
     "A sesizat incalcarea regulii X si a facut Y.";
   - nu combina doua garduri intr-un singur titlu de tip "GARD: A + B";
   - nu afisa mecanic toate campurile daca nu sunt relevante;
   - nu contine dumpuri tehnice, hashuri sau diagnostice lungi.
   - titlul chatului se citeste din transcript cand exista eveniment ai-title/custom-title;
     daca nu este disponibil, se spune explicit ca titlul este indisponibil.
   - promptul curent se ia direct din UserPromptSubmit; la hookurile ulterioare
     se poate recupera ultimul prompt user din transcript.

2. log tehnic.txt
   - jurnal complet pentru diagnostic;
   - are obligatoriu o SECTIUNE_COMUNA identica drept schema pentru toate gardurile;
   - apoi CANALE_CATRE_CLAUDE cu textele exacte;
   - apoi DETALII_SPECIFICE_GARDULUI.

SECTIUNEA_COMUNA din logul tehnic trebuie sa contina cel putin:
- versiunea schemei de log;
- data si ora Europe/Bucharest;
- sesiunea;
- hook event;
- numele folderului gardului din repo;
- activitatea principala;
- permissionDecision, daca exista;
- tool_name si target path, daca exista;
- repository root primit de la Claude Code;
- process.cwd;
- rootul runtime al pluginului si commitul lui Git;
- versiunea Node si platforma/arhitectura;
- repository-ul remote si clona locala folosite pentru logging;
- commitul repository-ului de log inainte de intrarea curenta;
- transcript_path;
- titlul chatului, cand poate fi determinat;
- promptul utilizatorului asociat activarii gardului.

CANALE_CATRE_CLAUDE trebuie sa pastreze exact, separat:
- CCN / systemMessage;
- additionalContext;
- permissionDecisionReason;
- orice alt mesaj catre Claude.

DETALII_SPECIFICE_GARDULUI contin informatiile suplimentare pe care numai gardul respectiv
le poate cunoaste: de exemplu status updater, hashuri de configuratie, liste PERMISE/INTERZISE,
trigger-ele si reminderele selectate sau alte date de diagnostic.

Helperul comun foloseste o clona tehnica separata, in /tmp, pentru fiecare sesiune.
La fiecare intrare de log:
- sincronizeaza clona cu branch-ul main;
- scrie AMBELE fisiere;
- face UN SINGUR commit pentru ambele;
- face push pe main.

Repository-ul de lucru YL nu mai este destinatia logului si nu trebuie murdarit
de logging. Hookurile individuale nu implementeaza clone/pull/commit/push si nu au
logger separat; toata aceasta responsabilitate ramane numai in helperul comun.

Pentru repository-ul remote exact de logging, sesiunea Claude Code trebuie sa aiba
`ion-motica/YL-Claude-garduri-Log-hooks-scris-de-Claude` in sursele autorizate, cu
acces push. Helperul nu cere si nu injecteaza un PAT propriu. Inainte de fiecare
operatie de retea, URL-ul efectiv al remote-ului origin trebuie sa coincida exact
cu URL-ul canonic asteptat; orice abatere opreste operatia. Daca proxy-ul Git spune
ca repository-ul nu este in setul autorizat al sesiunii, diagnosticul trebuie sa
indice explicit folosirea `add_repo` cu acces push si retrimiterea unui prompt.

In ambele loguri se folosesc randuri normale cu newline.
Nu comprima logul cu " | ".

REGULA CCN VS ADDITIONAL CONTEXT

Pentru hookurile sincrone folosite acum:
- systemMessage / CCN este mesaj vizibil utilizatorului;
- additionalContext este introdus in contextul lui Claude si il poate influenta;
- permissionDecisionReason de la PreToolUse deny este transmis lui Claude.

Nu presupune ca CCN si additionalContext sunt acelasi canal.
Orice canal prin care programul nostru trimite text lui Claude trebuie sa fie
inregistrat in logul de activitate.

Comportamentul exact trebuie verificat per eveniment nou,
deoarece Claude Code are exceptii pentru anumite hookuri si pentru hookuri async.

REGULA PENTRU LISTELE DE PROTECTIE

UserPromptSubmit poate genera/verifica intern listele efective PERMISE/INTERZISE,
dar nu le injecteaza automat in additionalContext doar pentru ca exista.

Pentru testarea curata si pentru separarea responsabilitatilor,
primul semnal catre Claude despre un fisier blocat trebuie sa poata veni
din PreToolUse atunci cand modificarea concreta este incercata.

PreToolUse aplica regulile de protectie repository-ului principal al sesiunii.
Daca tinta Edit/Write apartine unui ALT repository Git valid, nu aplica regulile YL
acelui repository si permite modificarea.
Daca tinta nu poate fi identificata ca apartinand unui repository Git, blocheaza fail-closed.
Nu confunda cwd-ul sesiunii cu repository-ul tintei.

REGULA PORTARULUI DE ACTUALIZARE

UserPromptSubmit intra prin infrastructura stabila din folderul:
"Hook UserPromptSubmit - cand trimit prompt update all garduri din github".

Portarul:
- verifica GitHub;
- instaleaza doar versiunea confirmata de CI;
- nu sterge modificari locale neasteptate;
- apoi ruleaza actiunile UserPromptSubmit.

Handlerul stabil si portarul raman infrastructura bootstrap;
schimbarea lor cere instalare explicita/rebuild, nu auto-inlocuire tacita.
