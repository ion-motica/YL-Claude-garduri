"Claude Code notice" de sub prompt.

REGULA GENERALA DE DENUMIRE

Pentru numele alese de noi, prefera denumiri lungi,
ne-generice si auto-explicative, care spun simultan:
- ce categorie de obiect este;
- ce rol concret are obiectul.

Exemple aprobate:
- handler_de_hook_UserPromptSubmit_pt_ciocanitoare.mjs
- motor_alegere_reminder_de_inserat.mjs
- reminder_ciocanitoare_injectat_in_prompt

Numele tehnice impuse de Claude Code raman neschimbate,
de exemplu UserPromptSubmit, PreToolUse, Stop etc.

Fisierul existent
"1 Sursa adevar/daca_detecteza_cuvinte_in_prompt_atunci_insereaza_asta.txt"
ramane cu aceasta denumire; nu il redenumi doar pentru uniformizare.

ORGANIZAREA TEXTULUI DIN CLAUDE CODE NOTICE

1. INTAI se afiseaza rezultatul util pentru user, nu detaliile tehnice.

Pentru UserPromptSubmit / ciocanitoare, forma incepe compact astfel:

S-a inserat: CP=<textul reminderului CP> ; crc=<textul reminderului crc> ; ...

Se afiseaza numai reminderele care au fost efectiv inserate.
Daca nu s-a inserat niciun reminder, forma este scurta:

S-a inserat: nimic.

Scopul acestei prime parti este ca userul sa poata vedea imediat
CE regula/reminder a ajuns in prompt, fara sa citeasca mai intai
informatii despre hookuri, fisiere, commituri sau instalare.

2. DUPA rezultatul util pentru user apar verificarile tehnice relevante.

Aici intra, dupa caz:
- statusul verificarii GitHub si al actualizarii intregului plugin;
- commitul GitHub verificat;
- lista/scurta clasificare a schimbarilor detectate;
- HOOKURI NOI detectate;
- SKILLS NOI detectate;
- BARZAUNI/COMPONENTE NOI necunoscute detectate;
- daca este necesar `/reload-plugins` si motivul concret;
- validator OK/eroare;
- ce hook a rulat;
- ce program/modul a fost folosit;
- alte verificari de functionare ale mecanismelor noastre.

Aceste informatii sunt grupate ca verificare tehnica si NU preced
rezultatul util pentru user.

3. LA SFARSIT apare sectiunea de prezenta a componentei,
cu numele tehnic al componentei, locul real din care ruleaza
si confirmarea ca functioneaza aici.

Exemplu:
PREZENTA COMPONENTEI:
Componenta tehnica: yl-claude-garduri@skills-dir
instalata in /root/.claude/skills/yl-claude-garduri
functioneaza aici.

Mesajul de prezenta se afiseaza si cand totul este OK,
nu doar cand exista eroare.

REGULA PORTARULUI DE ACTUALIZARE

UserPromptSubmit intra prin fisierul stabil:
"Hook UserPromptSubmit/program_portar_actualizare_intreg_plugin_din_GitHub_inainte_de_fiecare_prompt.mjs".

Portarul:
- verifica la fiecare prompt SHA-ul GitHub main printr-o interogare usoara;
- daca SHA-ul este identic cu cel local, NU face fetch;
- daca SHA-ul difera, face fetch, compara exact fisierele schimbate si actualizeaza pluginul local;
- verifica si raporteaza daca au aparut hookuri, skills sau alte componente/foldere noi;
- ruleaza apoi handlerul UserPromptSubmit din versiunea tocmai actualizata;
- daca s-a schimbat configuratia/componenta de plugin care necesita reincarcare, cere explicit `/reload-plugins`.

Fisierul portar de mai sus si calea lui sunt infrastructura stabila.
Nu il sterge si nu il redenumi intr-un update obisnuit, deoarece `hooks/hooks.json`
il foloseste ca punct de intrare persistent.

Scop general: userul vede mai intai CE S-A FACUT pentru promptul curent,
iar detaliile tehnice de verificare a functionarii instalatiilor noastre
raman in partea finala a Claude Code notice.
